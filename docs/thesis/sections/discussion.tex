\section{Discussion}

The current design emphasizes reproducibility and separation of concerns.
Dataset splitting is explicit and leakage-aware; preprocessing avoids irreversible
musical quantization; tokenization is configured and stored in YAML; xLSTM model
size is controlled through a small set of scaling parameters; training artifacts
are stored under \verb|experiments/| with resolved configs, checkpoints, metrics,
and summaries. This structure makes the validation results traceable: each
reported number can be connected back to a split file, tokenizer configuration,
training configuration, and checkpoint path.

The main experimental finding is that representation choice matters at least as
much as the small model and schedule changes tested so far. Tokenizer 11 was the
best configuration in the tokenizer-only autotuning run, but tokenizer 14 gives
the strongest downstream validation results. This difference is important because
it shows that a tokenization scheme should not be selected only by round-trip
fidelity or sequence compactness. For autoregressive training, the layout of the
event stream also changes the prediction problem seen by the model.

The medium-model follow-up is also informative, but in a negative way. It shows
that larger capacity and longer training do not automatically improve the current
validation metric. The run reaches its best checkpoint early and then diverges
from the validation objective while training loss continues to fall. This pattern
is consistent with overfitting on the 2,000-file subset, but it should not be
interpreted as proof that the medium architecture is worse in general. The
experiment changes model size, epoch count, and learning-rate schedule together,
so it identifies a weak training recipe rather than isolating one cause.

Validation loss remains only a proxy for generation quality, a limitation also
reflected in prior symbolic-music generation work that combines objective
metrics with qualitative or task-specific evaluation
\citep{dongMuseGANMultitrackSequential2017,ensMMMExploringConditional2020}.
It measures
next-token prediction against reference MIDI chunks, not whether sampled
continuations decode cleanly, avoid excessive repetition, preserve musical form,
or sound coherent. The current best candidates should therefore be evaluated
with generated-MIDI metrics and qualitative inspection before the thesis makes a
final model claim. In particular, the base tokenizer-14 batch-8 and batch-16
checkpoints are strong candidates for generation evaluation, while tokenizer-10
and the early best medium checkpoint remain useful comparison points.

The practical value of the current work is that it narrows the next stage. The
pipeline no longer needs to treat every tokenizer and schedule as equally likely.
The evidence supports tokenizer 14 as the default downstream representation,
batch size 8 or 16 as the most relevant base-model setting, and validation-based
checkpoint selection as necessary because final checkpoints can be misleading.
The remaining work is therefore not basic infrastructure, but final evaluation:
generate continuations from held-out prompts, compute generated-MIDI metrics,
inspect representative outputs, and compare the selected xLSTM checkpoint against
the later Transformer baseline under matched conditions.
